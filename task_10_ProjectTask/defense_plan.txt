План защиты проекта
Вариант 9. Техподдержка: заявки и обращения

1. Цель работы

В этой работе я делал проект по варианту 9: техподдержка, заявки и обращения.

Цель проекта - создать аналитические витрины данных, которые помогают оценивать:
- качество работы службы поддержки;
- нагрузку на сотрудников;
- скорость решения заявок;
- распределение заявок по категориям, приоритетам и статусам.


2. Какие данные используются

Для проекта были сгенерированы синтетические данные по предметной области техподдержки.

Используются следующие таблицы:
- users.csv - пользователи, которые создают заявки;
- categories.csv - категории обращений;
- support_staff.csv - сотрудники службы поддержки;
- tickets.csv - заявки пользователей.

В таблице tickets.csv есть основные поля заявки:
- дата создания;
- дата обновления;
- дата решения;
- статус;
- приоритет;
- категория;
- назначенный сотрудник;
- JSON-комментарии к заявке.


3. Структура пайплайна

Обработка данных автоматизирована с помощью DAG в Airflow.

Пайплайн состоит из следующих шагов:

generate_data -> load_raw -> transform -> create_mart -> visualize

Описание шагов:

generate_data - генерирует исходные CSV-файлы с пользователями, категориями, сотрудниками и заявками.

load_raw - имитирует загрузку данных в raw-слой.

transform - подготавливает и обогащает данные: рассчитывает время решения заявки, приводит даты, добавляет нужные признаки.

create_mart - создает итоговые аналитические витрины.

visualize - строит графики для визуального анализа результатов.


4. Какие витрины созданы

В проекте созданы две итоговые витрины.

Первая витрина:

mart.support_kpi

Она показывает эффективность сотрудников поддержки.

Поля витрины:
- staff_id - идентификатор сотрудника;
- full_name - ФИО сотрудника;
- tickets_resolved - количество решенных заявок;
- avg_resolution_time_hours - среднее время решения заявки в часах;
- backlog - количество открытых заявок, назначенных на сотрудника.

Вторая витрина:

mart.ticket_stats

Она показывает статистику по категориям и приоритетам заявок.

Поля витрины:
- category - категория заявки;
- priority - приоритет заявки;
- avg_resolution_time - среднее время решения заявки;
- total_tickets - общее количество заявок в группе.


5. Как считаются показатели

tickets_resolved считается как количество заявок сотрудника с финальным статусом:

resolved или closed

avg_resolution_time_hours считается как разница между временем решения и временем создания заявки:

resolved_at - created_at

После этого результат переводится в часы.

backlog считается как количество заявок, которые еще не завершены.

К таким статусам относятся:

new, in_progress, waiting

total_tickets считается как количество заявок в группе:

category + priority


6. Визуализация

Для анализа результата были построены 4 графика:

- среднее время решения по сотрудникам;
- количество заявок по категориям;
- динамика создания заявок по дням;
- круговая диаграмма статусов заявок.

Графики лежат в папке:

task_10_ProjectTask/outputs/figures


7. Как проверить работу проекта

Airflow запускается через Docker из папки:

task_7_Airflow_dags

Команда для запуска:

docker compose up -d

После запуска нужно открыть веб-интерфейс Airflow:

http://localhost:8080

Логин и пароль:

airflow / airflow

В Airflow нужно найти DAG:

support_project_pipeline

Далее нужно включить DAG, если он выключен, и запустить его вручную через Trigger DAG.

После выполнения все задачи должны быть зелеными:

- generate_data;
- load_raw;
- transform;
- create_mart;
- visualize.

task_10_ProjectTask/data/mart

9. Итоговый вывод

В результате был построен полный ETL-пайплайн для анализа работы службы технической поддержки.

Данные генерируются автоматически, затем проходят этап обработки, после чего на их основе создаются две аналитические витрины и визуализации.

Airflow автоматизирует выполнение всех шагов, поэтому весь процесс можно запускать повторно одной кнопкой через веб-интерфейс.
